# ممیزی دستهٔ ادامهٔ ۴

## دامنه و روش

۲۰ ورودی نخستِ دارای وضعیت «درانتظار» در `AUDIT_FILE_STATUS.md`، کامل و خط‌به‌خط خوانده شدند. برای هر فایل نقش، رفتار، call path، وابستگی‌ها، error handling، multi-project scope، تست مرتبط و محدودیت‌ها بررسی شد. امنیت عمداً خارج از دامنه بود؛ بنابراین ادعاهای مربوط به توکن، Origin، traversal و مانند آن به‌عنوان finding امنیتی گزارش نشده‌اند. شواهد زیر با path/line ارجاع داده شده‌اند.

## فایل‌های بررسی‌شده

1. `semantic-engine/src/blueprint/EntityMapExtractor.ts` — extractorهای entity/workflow؛ ورودی `ProjectIndex` و `apiMap`، خروجی mapping مرتب‌شده. Entity از symbolهای مدل/ORM و fieldهای فرزند ساخته می‌شود؛ workflow از callGraph و حداکثر ۲۰ گام، با انتخاب confidence بالاتر. وابستگی‌ها: project-index types، fileRole، hash و blueprint types. خطاها عمدتاً fail-closed با skip هستند؛ `sourceOf` اختیاری است. scope پروژه از همان ProjectIndex است و cross-project join انجام نمی‌شود. محدودیت‌های صریح: ORM و table name با regex محدود، relationها همیشه `null`، workflow فقط یک مسیر خطی و API بدون handler حذف می‌شود. تست مستقیم این فایل در این batch وجود ندارد.
2. `semantic-engine/src/blueprint/index.ts` — barrel export برای `BlueprintGenerator` و options؛ call path فقط import عمومی blueprint است؛ وابستگی داخلی همان `BlueprintGenerator`. مدیریت خطا/محاسبه scope ندارد.
3. `semantic-engine/src/blueprint/moduleResponsibility.test.ts` — تست regression مسئولیت module با رأی‌گیری روی فایل‌های همان module؛ fixtureهای چندفایلی، تست‌فایل‌ها و ترتیب ورودی را پوشش می‌دهد و به `BlueprintGenerator.generate` متصل است. محدودیت: فقط assertion روی label است و الگوریتم را مستقیم تست نمی‌کند.
4. `semantic-engine/src/cli/HttpGuard.test.ts` — تست integration سرور HTTP کوچک برای `HttpGuard`: token، Origin، سقف body، loopback، method/path و پاسخ خطا. وابستگی Node `http/net`. هر server در finally بسته می‌شود. امنیت خارج از scope این ممیزی است.
5. `semantic-engine/src/cli/HttpGuard.ts` — guard جلوی POST `/mcp`: method/path، header، body reader سقف‌دار و تحویل handler؛ handler error به 500 تبدیل می‌شود و stream/response مدیریت می‌شود. call path در این فایل تست‌های HttpGuard و در runtime سرورهای CLI است. وابستگی Node crypto/http. محدودیت: `isLocalOrigin` و token policy ساده و مخصوص همین guard هستند؛ integration با هر server باید جداگانه bind/host را تنظیم کند.
6. `semantic-engine/src/cli/args.ts` — parser بدون dependency؛ command، positional و optionهای camelCase/boolean/string را می‌سازد و `stringOption`/`boolOption` مصرف‌کننده‌ها هستند. خطاهای semantic flag شناخته نمی‌شوند و parser صرفاً ساختاری است؛ مقدار منفی که با `-` آغاز شود positional/value تلقی نمی‌شود. تست مستقیم در `cli.test.ts` دارد.
7. `semantic-engine/src/cli/cli.test.ts` — تست parser و CLI جداپروسه‌ای برای help/version/index/query/doctor، artifact location، stdout/stderr و exit code؛ بخش‌های واقعی با `describeIfBuilt` فقط در صورت build اجرا می‌شوند. وابستگی به binary/dist و fixture؛ بخش built در محیط فعلی قابل اجرا نیست.
8. `semantic-engine/src/cli/commands/artifactLocationDefault.test.ts` — تست `runIndex` برای حالت explicit `in-root` و `--out`؛ env را در before/after حفظ می‌کند و عدم نوشتن در data root را می‌سنجد. call path مستقیم به index command است، نه wrapper CLI. scope یک workspace موقت است.
9. `semantic-engine/src/cli/commands/artifactLocationExternal.test.ts` — تست `runIndex` در external location، migration legacy، explicit `--out` و `--project-id`؛ وابستگی ProjectIdentity و config env. cleanup کامل دارد. محدودیت: همزمانی/خرابی filesystem را تست نمی‌کند.
10. `semantic-engine/src/cli/commands/cache-command.ts` — commandهای list/clean/export/import برای artifactهای data root؛ listEntries و directorySize خواندنی، clean با dry-run/force، import/export با copyTree. call path از main به `runCache`; وابستگی DataRootResolver، ProjectPaths و registry. خطاهای read/stat اغلب به empty/skip تبدیل می‌شوند و خطای ورودی به usage برمی‌گردد. project selection بر اساس directory name است و command خودش cross-project merge نمی‌کند؛ registry برای جلوگیری از overlap خوانده می‌شود. محدودیت‌های عملکردی پایین‌تر ثبت شده است.

## Findings قطعی

**هیچ finding قطعیِ غیرامنیتی با evidence کافی در این ۲۰ فایل ثبت نشد.** رفتارهای حساسِ HttpGuard و cache عمداً در این ممیزی به‌عنوان امنیت ارزیابی نشدند. تست‌های موجود نیز عمدتاً regression/acceptance هستند و ناسازگاری قطعی از خودِ متن یا call path به دست نیامد.

## POTENTIAL / UNVERIFIED

1. **POTENTIAL — اعتبارسنجی ناقص `--older-than`:** در `cache-command.ts:241-247`، اگر `parseDuration` برای مقدار نامعتبر `null` بدهد، selector تهی می‌شود؛ در `:249-264` در حالت non-force dry-run موفقیت با «هیچ موردی» برمی‌گردد و در force هم `:266-285` success/removed-empty ممکن است برگردد، نه usage. این فقط در صورتی finding محصولی است که قرارداد CLI برای مقدار malformed کد usage بخواهد؛ تست `cacheCommand.test.ts:150-154` فقط نبود selector را پوشش می‌دهد و مقدار malformed را نه.
2. **POTENTIAL — عبور گزینه‌های path به tool params در query:** `query-command.ts:18-19` فقط `index,json,root,help,version` را reserved می‌کند؛ سپس `:85-89` همهٔ گزینه‌های دیگر را به params ابزار می‌فرستد. بنابراین `--data-dir`، `--project-id`، `--out` یا `--artifact-location` (که resolver/migration ممکن است مصرف کرده باشند) نیز به ابزار می‌رسند. قطعی نیست که ابزارهای فعلی این کلیدها را رد یا نادیده بگیرند؛ برای اثبات باید قرارداد `AiToolRegistry`/validator هر ابزار و CLI help بررسی شود.
3. **POTENTIAL — workflow سقف گام نامعتبر:** `EntityMapExtractor.ts:201-214` فقط default می‌دهد و `maxSteps` را validate نمی‌کند؛ `:232-234` برای صفر/منفی هیچ stepی می‌سازد و خروجی خالی می‌شود. معلوم نیست caller هرگز مقدار غیرمثبت ندهد؛ تست مرتبطی در این batch وجود ندارد.
4. **UNVERIFIED — extractorهای ORM با regex روی کل source:** `EntityMapExtractor.ts:102-121` و `:159-164` marker را با regex روی source خام تشخیص می‌دهند؛ comment/string یا symbol unrelated می‌تواند marker را match کند. اثبات false-positive نیازمند parser/fixture خارج از این ۲۰ فایل است.

## تست‌ها
